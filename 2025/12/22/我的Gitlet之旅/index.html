我的Gitlet之旅

发表于 2025-12-22 更新于 2025-12-23

init

初始化一个目录，即添加一个.gitlet目录

  1. 创建子目录 (objects, refs)

  2. 生成Initial Commit对象

  3. 创建 master 指针指向该 Commit

  4. 新建一个暂存区，这里我创建了一个辅助类StagingArea.java,后面会贴出来

add

将文件添加到暂存区

add 命令并不只是将文件名放入列表。它必须读取文件内容，计算哈希，并在暂存区中更新映射

  1. 暂存区应该在.gitlet中的某个位置

    • 获取HEAD指向的id

  2. 如果文件没变，使用add无效

  3. 如果工作区的内容与commit里的内容相同，则删除暂存区内容

  4. 记得持久化

commit

保存已经存储了的文件的快照，commit 对象本身不存文件内容（只存 blob 引用/哈希）。

将暂存区的文件提交到commit里

快照跟踪的是文件名及其对应的哈希值

所以commit的作用没有把内容硬存盘这一步，而是提供对add中文件的快照

  1. 每个提交应包含其生成的日期和时间。

  2. 每个提交都有一个与之关联的日志消息

  3. 刚刚进行的commit成为“当前提交”，head 指针现在指向它。之前head指向的commit是此commit的父提交。

  4. 每个提交都由其 SHA-1 id 标识，该 id 必须包括其文件的文件（blob）引用、父引用、日志消息和提交时间。

  5. commit后暂存区内容被清空

  6. commit命令从不添加、更改或删除工作目录中的文件（除了 .gitlet 目录中的那些）

  7. 被跟踪的文件从工作目录中丢失或在工作目录中被更改 不 算是失败。只需完全忽略 .gitlet 目录之外的所有内容。

rm

删除暂存区或硬盘中(工作目录)的文件，但是无法删除commit里的记录

  1. 如果文件既未暂存也未被 head 提交跟踪，打印错误消息 No reason to remove the file.

  2. 如果当前文件在暂存区，则将他从暂存区移除

  3. 如果文件已被commit跟踪，则将他的放入“待删除暂存区”，并将目录文件删除

  4. 已被commit跟踪，但是文件已经不存在于文件目录

log

从当前 head 提交开始，沿着提交树向后显示每个提交的信息

  • HEAD → 找到当前分支文件

  • 分支文件 → 得到 head commitId

  • 去 objects/<commitId> 读出 commit

  • 打印它，然后用 commit.parent 更新 commitId

  • 重复直到 parent = null

  • 所以 log 本质是：从一个入口 commit 出发，沿 parent 链遍历并打印

global-log

类似于 log，除了显示所有曾经进行的提交的信息。提交的顺序无关紧要。

把对象库里所有 commit 都打印一遍（顺序无所谓）

  • 扫描 objects/ 下所有文件名（id）

  • 过滤出“哪些是 commit”（因为里面还有 blob）

  • 对每个 commit 打印同样的格式

  • 扫数据库（也就是我们的objects）

find

打印出所有具有给定提交消息的提交 id，每行一个。如果有多个这样的提交，它会将 id 打印在单独的行上。

find 和 global-log 的结构几乎一模一样：

  • 都是扫 objects

  • 都要过滤 commit

  • 差别只是：

    • global-log：全部打印

    • find：只打印 message 完全匹配的 commitId；没有则报错

  • 数据库查询（WHERE message = ?）

status

显示当前存在哪些分支，并用 * 标记当前分支。还显示哪些文件已暂存以进行添加或移除。

它几乎不关心历史链长啥样，它关心的是现在工作区和暂存区的状态

  • refs/heads + HEAD：列分支、标当前分支

  • index：列 staged 和 removed

  • 工作区 CWD + HEAD commit 的快照（commit.map） + index：对比出

    • 未暂存的修改（modified not staged）

    • 未跟踪文件（untracked）

  • 工作台对比（CWD vs HEAD vs INDEX）

checkout

Checkout 是一种通用命令，根据其参数的不同可以做几件不同的事情。

checkout 的三种用法：

  • checkout -- file：commit 来源 = 当前 HEAD commit

  • checkout commitId -- file：commit 来源 = 指定的 commit

  • checkout branch：commit 来源 = 目标分支的 head commit（并且还要移动 HEAD 指向新分支）

branch

创建一个具有给定名称的新分支，并将其指向当前 head 提交。

  • 不会产生新 commit

  • 不会改工作目录文件

  • 只是多了一个名字 → commitId 的映射

  • 如果同名分支已经存在：打印 A branch with that name already exists.

rm-branch

删除具有给定名称的分支。这仅仅意味着删除与分支关联的指针；这并不意味着删除在该分支下创建的所有提交，或类似的东西。

  • 分支不存在：A branch with that name does not exist.

  • 试图删除当前分支：Cannot remove the current branch.

  • commit 节点是不可变的，你只能加新节点，不能改旧节点；删分支只是“忘记一个入口”，不等于抹掉历史本体。

reset

检出由给定提交跟踪的所有文件。删除该提交中不存在的被跟踪文件。还将当前分支的 head 移动到该提交节点。

任何会覆盖/删除工作区文件的命令（checkout 分支 / reset / merge）都必须先做 untracked 覆盖检查。

  • 把给定 commit 所跟踪的所有文件检出到工作目录

  • 删除当前被跟踪但在目标 commit 快照里不存在的文件（即“目标快照没有的跟踪文件要移除”）

  • 把当前分支的 head 指针移动到那个 commit 节点

  • 清空暂存区 并且它几乎就是“对任意 commit 做一次 checkout，同时还改变当前分支头”。

  • commit id 可以像 checkout 一样用缩写前缀。

  • 如果 commit 不存在：No commit with that id exists.

  • 如果当前分支里有某个工作文件是 untracked，并且 reset 会覆盖它：打印 There is an untracked file in the way; delete it, or add and commit it first. 而且要求 在做任何事之前就检查并退出。

merge

将给定分支的文件合并到当前分支中。

把两条历史线“重新接线”，生成一个双亲提交（而且可能冲突）

  • given 改了、current 没改：用 given 版本覆盖，并且自动 stage。

  • current 改了、given 没改：保持 current 不动。

  • 两边都没改：保持不动。

  • 某文件只存在于 current（不在 split，也不在 given）：保持不动。

  • 某文件只存在于 given（不在 split，也不在 current）：检出 given 并 stage。

  • split 有、current 没改、given 删除了：删掉（并变成 untracked/移除），相当于“接受 given 的删除”。

  • split 有、given 没改、current 删除了：保持 absent。

  • 两边“改动方式不同”：冲突（包括内容不同、或一边改一边删、或 split 不存在但两边新建且内容不同）。

    merge 的失败条件很多，而且顺序很要命（因为很多检查要求“在做任何事之前”就退出）：

    • 暂存区里有 staged additions 或 removals：You have uncommitted changes.

    • given 分支不存在：A branch with that name does not exist.

    • merge 自己：Cannot merge a branch with itself.

    • 如果当前 commit 中存在 untracked 文件，并且 merge 会覆盖或删除它： There is an untracked file in the way; delete it, or add and commit it first. 并且要求 在做任何事之前就检查
